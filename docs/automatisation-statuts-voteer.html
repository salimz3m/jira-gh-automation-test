Automatisation des statuts Jira pilotée par GitHub

Un ticket saisi dans une branche, une PR ouverte ou un déploiement : le statut Jira se met à jour tout seul, avec une trace horodatée à chaque étape. Mécanisme validé de bout en bout sur un environnement de test, prêt à être transposé sur l'organisation Voteer.

01 · Résumé

L'essentiel en une page

Les statuts des tickets Jira suivent aujourd'hui le rythme des mises à jour manuelles : ils arrivent souvent en retard, ou pas du tout. L'automatisation présentée ici relie directement le travail réel — branches, pull requests, déploiements — au cycle de vie du ticket.

Chaque action laisse une trace dans le ticket (commentaire avec lien vers le run GitHub), ce qui rend vérifiable, à tout moment, ce qui a été fait, quand, et par quel pipeline.

02 · Démarche et suivi

Les étapes choisies, et le déroulé du test

Choix d'architecture : appels directs à l'API Jira

Deux approches étaient possibles :

  • Approche « native » — application GitHub for Jira + règles Jira Automation. Puissante, mais les règles se créent uniquement à la main dans l'interface Jira : rien n'est versionné, rien n'est reproductible, et chaque projet doit être reconfiguré manuellement.
  • Approche retenue « API REST » — le workflow GitHub Actions appelle directement l'API Jira (transition de statut et commentaire) avec un token stocké dans les secrets du dépôt. Tout vit dans le dépôt : versionné, relu comme du code, dupliqué en quelques minutes d'un projet à l'autre.

L'approche retenue a été testée de bout en bout. Elle n'exclut pas l'approche native : les jobs de déploiement utilisent des environnements GitHub, ce qui les rend compatibles avec un branchement ultérieur sur GitHub for Jira.

Convention de branches

La clé Jira complète doit figurer dans le nom de branche et dans le titre de la PR :

FormatExemple
Sprint/Fix/<clé>-<nom>Sprint/Fix/VOTEER-12-correction-login
feature/<clé>-<nom>feature/VOTEER-12-correction-login

Le workflow extrait la clé automatiquement (motif [A-Z]+-[0-9]+) du nom de branche, puis du titre de la PR. Aucun autre outil n'est nécessaire pour que le lien se fasse.

Déroulé du test — journal horodaté

Test réalisé le 18 novembre 2026 sur un dépôt dédié et un ticket véhicule, dans un projet Jira sans enjeu. Chaque étape a été déclenchée comme elle le sera en production, puis vérifiée dans Jira.

  1. 11:43Push de la branche feature/SCRAP-18-… → ticket passé En cours, commentaire avec le nom de la branche.
  2. 11:43PR #1 ouverte → commentaire « PR ouverte » avec son lien.
  3. 11:44PR fusionnée en squash, branche supprimée → commentaire « fusionnée dans main ».
  4. 11:45Déploiement dev → commentaire avec le lien du run Actions.
  5. 11:45Déploiement staging → commentaire avec le lien du run Actions.
  6. 11:46Déploiement prod → ticket passé Terminé, commentaire avec le lien du run.

Ce que contient le dépôt

  • .github/workflows/jira-sync.yml — le workflow unique : trois déclencheurs (push, pull request, lancement manuel), trois jobs courts, aucune dépendance externe.
  • .github/scripts/jira.sh — le script d'appel : transition par nom de statut (aucun identifiant fragile codé en dur), commentaire au format natif Jira, diagnostic HTTP complet en cas d'échec.
  • Trois secrets de dépôt : JIRA_BASE_URL, JIRA_USER_EMAIL, JIRA_API_TOKEN. Le token reste dans GitHub et n'est jamais exposé dans le code.

Le test a aussi servi à corriger trois défauts réels avant mise en production

  • Format du corps de requête pour les transitions Jira (structure transition.id attendue par l'API).
  • Format du commentaire (Jira exige un corps structuré ADF, pas du texte brut).
  • Diagnostic : les erreurs HTTP de Jira sont désormais affichées en clair dans le log du run, au lieu d'un échec muet.

C'est précisément l'intérêt d'un environnement de test : ces trois points auraient coûté une demi-journée de tâtonnement sur le dépôt réel.

03 · Périmètre capable

Ce que l'automatisation sait faire — et ce qu'elle ne fait pas

Ce qu'elle couvre

CapacitéDétail
Transitions de statutPar nom de statut cible — résiste aux changements d'identifiants et fonctionne sur tout workflow Jira, y compris les statuts personnalisés (ex. « Deployed on Dev »).
CommentairesTexte horodaté avec liens cliquables vers la PR et le run GitHub. Base de l'audit et des notes de version.
Événements GitHubTout événement Actions : push, PR, déploiement, release, tag, échec de build, lancement manuel.
MultiprojetUn même dépôt peut piloter plusieurs projets Jira (le script lit la clé dans la branche, le projet en découle).
ExtensibleL'API Jira permet aussi d'assigner, d'étiqueter, de renseigner des champs personnalisés, de lier des tickets ou de gérer des versions. Ces briques s'ajoutent au même script si le besoin apparaît.
TransposableInstallation identique sur n'importe quel dépôt GitHub : copier deux fichiers, ajouter trois secrets.

Ce qu'elle ne fait pas (limites assumées)

  • Elle ne remplace pas la discipline de branche. Sans clé Jira dans le nom de branche ou le titre de PR, aucun lien n'est établi. C'est le principal point de vigilance à l'adoption.
  • Le token a un propriétaire. Le token API appartient à un compte Atlassian ; si ce compte disparaît, l'automatisation s'arrête. Recommandation : créer un compte de service dédié et en faire le propriétaire du token.
  • Les statuts doivent exister dans le projet. Si un projet voteer n'a pas de statuts « dev / staging / prod », il faut soit les ajouter au workflow (2 minutes), soit se limiter aux commentaires pour ces environnements.
  • Les droits suivent le compte. Le porteur du token doit avoir le droit de transitionner sur les projets concernés.
  • Idempotence à parfaire. Re-pousser sur une branche déjà « En cours » produit aujourd'hui un run en échec (sans effet sur Jira, mais bruyant). Correction déjà identifiée : traiter « transition indisponible » comme un succès quand le ticket est déjà dans l'état visé.
  • Bruit possible. Multiplier les événements multiplie les commentaires. Recommandation de démarrage : branche, PR fusionnée, prod — puis ajouter dev/staging si l'équipe les trouve utiles.
  • Coût d'exécution : chaque événement consomme ~10 à 20 secondes de runner GitHub Actions — négligeable à l'échelle d'une organisation.

Prérequis techniques pour voteer

  • Les trois secrets du dépôt (URL Jira, email, token API).
  • L'approbation de GitHub CLI par un propriétaire de l'organisation — ou un token à portée limitée — pour les opérations d'installation.
  • Le nom des statuts réels du projet Jira voteer, pour caler le mapping.

04 · Gain réel

Ce que ça change à l'échelle de centaines de tickets

Sur un projet de quelques tickets, la saisie manuelle des statuts tient encore. Sur des centaines de tickets, le suivi décroche : les tableaux de bord affichent un état vieux de plusieurs jours, et le temps du chef de projet part en relances de mise à jour au lieu d'analyse.

Traçabilité des livraisonsReconstituée à la main, par mémoire ou par git logChaque ticket porte le lien de son run de déploiement
Adoption du processusUne procédure à connaître et à respecterLa branche fait la procédure : rien à apprendre de plus
Passage à l'échelleCoût linéaire avec le nombre de ticketsCoût constant, identique à 30 ou à 3 000 tickets

Les trois gains qui comptent vraiment

  1. Le tableau de bord dit la vérité. Quand les statuts suivent les vrais événements, un filtre JQL devient une source de décision : savoir quels tickets attendent une validation produit, lesquels sont déployés mais pas encore terminés, lesquels traînent depuis trois sprints.
  2. « Qu'est-ce qui est parti en prod cette semaine ? » devient une requête. Chaque ticket terminé contient le lien du déploiement qui l'a livré — la réponse existe, horodatée, sans réunion ni fouille dans les logs.
  3. Le temps libéré est le temps du chef de projet, pas celui de l'équipe de dev. Les relances de statut, les tableaux à corriger avant la réunion, les allers-retours « tu peux bouger le ticket ? » disparaissent.

Message honnête sur le gain

Le gain dépend d'une seule habitude : mettre la clé du ticket dans les branches. C'est une contrainte légère, et c'est la plus faible qu'on puisse demander à un développeur pour obtenir un suivi fiable. Le reste — relances, saisies, corrections — disparaît sans effort supplémentaire.

05 · Adaptation Asana

Et si Voteer passait (aussi) par Asana

Le mécanisme ne dépend pas de Jira : c'est un workflow GitHub qui parle à une API. Asana expose lui aussi une API REST complète. La transposition demande de réécrire le script d'appel, pas l'architecture. Le côté GitHub — branches, PR, déploiements, secrets — reste strictement identique.

Équivalence des concepts

Jira (actuel)Asana (adaptation)
Ticket VOTEER-12 (clé native)Tâche Asana — identifiée par un identifiant technique (GID) ; la clé VOTEER-12 reste la convention dans le nom de la tâche
Statut de workflowSection du tableau (colonnes « À faire / En cours / Terminé », ou sections d'environnement)
Transition par nom de statutDéplacement de la tâche vers une section cible de son projet
Commentaire JiraCommentaire (story) sur la tâche
Recherche par clé d'issueRecherche de la tâche par son nom dans le projet — moins robuste si les tâches sont renommées
Auth : Basic email + token APIAuth : Bearer PAT Asana (une seule valeur)
Secrets : JIRA_BASE_URL, JIRA_USER_EMAIL, JIRA_API_TOKENSecrets : ASANA_TOKEN, ASANA_PROJECT_GID (et les GID de sections)

Ce qui change, ce qui ne change pas

  • Inchangé : déclencheurs GitHub, extraction de la clé dans la branche/PR, jobs par environnement, secrets du dépôt, lien des runs dans les commentaires.
  • À adapter : une version asana.sh remplaçant jira.sh (même structure : une commande « déplacer vers section » et une commande « commenter »), et la résolution des identifiants de sections — à relever une fois à la configuration.
  • Effort estimé : environ une demi-journée à une journée, dont l'essentiel pour caler la convention de nommage et les sections cibles.

Limites propres à Asana

  • Pas de clé native lisible : Jira génère VOTEER-12, Asana non. La convention doit donc vivre dans le nom de la tâche, ce qui impose de ne pas la renommer.
  • Recherche par nom fragile : si une tâche change de nom, le lien casse. Remède : conserver la clé dans un champ personnalisé, ou une table de correspondance dans le dépôt.
  • Limite de débit plus stricte qu'aucun usage réel de ce workflow n'atteindra : une poignée d'appels par événement.
  • Statuts = sections : le modèle est plus souple que le workflow Jira, mais moins structuré — les transitions ne sont pas contrôlées.

Les deux outils ensemble, si nécessaire

Rien n'interdit d'informer Jira et Asana depuis le même workflow : deux appels successifs dans le même job. C'est une ligne ou deux à ajouter, utile pendant une période de transition ou si des parties prenantes suivent le projet dans Asana.

06 · Mise en œuvre

Passer du test à voteer

Le test a déjà répondu aux questions d'architecture. Il reste à transposer — et à décider de ce qui convient à voteer.

  1. Obtenir l'accès à l'organisation — un propriétaire de @voteer approuve GitHub CLI, ou un token à portée limitée est créé pour les opérations d'installation.
  2. Identifier le projet Jira de voteer et lister ses statuts réels. Si les états « dev / staging / prod » n'existent pas, choisir entre les ajouter au workflow ou se limiter aux commentaires pour ces environnements.
  3. Créer un compte de service (ou réutiliser le compte choisi) et générer son token API ; le conserver dans les secrets du dépôt voteer, jamais dans le code.
  4. Installer les deux fichiers dans le dépôt voteer et brancher les étapes Jira dans les vrais jobs de déploiement, après les étapes de mise en production.
  5. Durcir le script avant généralisation — tolérer proprement le cas « ticket déjà dans le statut visé », pour qu'une re-poussée ne produise jamais un run rouge inutile.
  6. Piloter sur 3 à 5 tickets réels, vérifier chaque effet, puis élargir. Décider à ce moment-là si dev et staging commentent aussi, ou si la prod suffit.

Ce que la documentation ne remplace pas

La décision d'élargir aux autres statuts et aux autres projets se prendra sur les données du pilote : nombre de commentaires générés, utilité perçue par l'équipe, ajustements de convention. C'est une décision d'organisation, pas une décision technique.
